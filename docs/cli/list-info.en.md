# Discovery: list and info

The `list` and `info` subcommands are the discovery surface — together they
turn an installed extension into a printable map of available tasks, envs,
robots, and the dotted-path keys that `play` / `train` can override.

## Listing the registry

`list KIND` enumerates one of the three global registries (`robots`, `envs`,
`tasks`). The command imports every discovered extension first, so the listing
reflects the current install set.

```bash
uv run genelab list robots
uv run genelab list envs
uv run genelab list tasks
```

Each row prints the registered name, description, and a per-entry detail line
(for tasks: `env=..., robot=..., trainable=...`; for envs / robots: the first
few scalar cfg fields). Tasks that registered `examples=[...]` strings via
`register_task(..., examples=[...])` show an `(N example(s))` suffix.

## Inspecting a task

`info NAME` resolves a single registered name and prints a detail panel. The
lookup falls through tasks → envs → robots in that order and exits with the
combined available-name listing when nothing matches.

```bash
uv run genelab info GeneLab-Sensors-Showcase-v0
```

The task panel contains three sections:

1. **Description and meta** — the one-line description plus the `env=...,
   robot=..., trainable=...` strip pulled from the task cfg.
2. **Overridable cfg paths** — a three-column table (`Path`, `Type`,
   `Default`) generated by walking the cfg dataclass tree depth-first. Field
   names beginning with `_` are skipped. Sub-dataclasses are expanded inline
   under their parent's dotted path.
3. **Examples** — the verbatim `examples=[...]` lines the extension supplied at
   registration time. They are display-only — `info` does not run them.

The same panel renders for envs and robots, but without the `env / robot /
trainable` meta strip.

## Override paths

Every row in the "Overridable cfg paths" table is the exact dotted path that
`play` and `train` accept on the command line. The CLI forwards each
`--<a.b.c> VALUE` flag into `genelab.configs.apply_overrides`, which coerces
the value against the target field's type hint at config build time.

| `info` row | Equivalent override flag |
|---|---|
| `env.simulation.vis` (bool, false) | `--vis` (shortcut) or `--env.simulation.vis true` |
| `env.simulation.gpu` (bool, false) | `--gpu` (shortcut) or `--env.simulation.gpu true` |
| `env.simulation.steps` (int, 240) | `--steps 500` (shortcut) or `--env.simulation.steps 500` |
| `env.simulation.dt` (float, 0.01) | `--dt 0.005` (shortcut) or `--env.simulation.dt 0.005` |
| `env.rewards_cfg.track_lin_vel.weight` (float, 1.0) | `--env.rewards_cfg.track_lin_vel.weight 2.0` |
| `env.rewards_cfg.track_lin_vel.params.std` (float, 0.25) | `--env.rewards_cfg.track_lin_vel.params.std 0.5` |
| `env.scene.env_spacing` (tuple, `(2.0, 2.0)`) | `--env.scene.env_spacing 3.0,3.0` |
| `env.scene.batch_render` (bool, false) | `--env.scene.batch_render true` |

The four simulation shortcuts (`--vis`, `--gpu`, `--steps`, `--dt`) rewrite to
the `env.simulation.{vis,gpu,steps,dt}` paths before forwarding, so they show
up in profiler-trace argv exactly like an explicit override would.

## Examples

A short discovery loop for the inverted-pendulum task:

```bash
# Confirm the extension is installed and pick a task id.
uv run genelab list tasks | grep Pendulum

# Drill into one task — copy a dotted path from the "Overridable cfg paths" table.
uv run genelab info GeneLab-Inverted-Pendulum-v0

# Run the task with overrides applied.
uv run genelab play GeneLab-Inverted-Pendulum-v0 --vis --steps 240 \
    --env.rewards_cfg.pole_upright.weight 5.0
```

The same flow works against envs and robots: `genelab info FrankaPandaCfg` (a
robot) reveals every `ArticulationCfg` field including the per-group
`actuators.*.stiffness` and `default_joint_pos.*` keys.
